## 결정한 것 (왜 그렇게 정했나)

- **느린 구글 호출을 `after`(next/server)로 화면 뒤로** (AI 판단) — 저장 버튼이 2~4초 걸리던 이유의
  대부분이 구글 왕복 2번이었다. 저장은 이미 끝난 상태라 화면을 먼저 넘기고 구글은 뒤에 반영한다.
  실패하면 전처럼 `sync_log` 에 남는다. 라이브에서 "빨라졌고 구글에도 올라왔다"로 확인됨.
- **낙관적 업데이트는 쓰지 않음** (사장님 질문에 답변) — 화면을 떠나는 흐름이고, 돈 기록이라
  "저장됨"을 보여줬다가 되돌리는 비용이 크고, 느린 진짜 원인을 가리기만 한다.
  대신 **정산 완료 토글**은 낙관적 업데이트가 어울리는 자리라고 남겨 둔다.
- **중복 방지는 '멱등성 키' 대신 '같은 내용 재전송 차단'** (AI 판단) — 키 방식은 DB 칸을 새로 만들어야
  하고, 배포와 SQL 실행 사이의 시간 차가 10-24 사고의 원인이었다. 1분 안에 날짜·구분·항목·금액·
  고객명·패키지·채널이 모두 같은 건이 또 들어오면 먼저 저장된 건으로 넘긴다 (`sameLedgerRow`).

- **밤+밤샘은 밤샘 값까지가 패키지 값** — 옵션으로 또 고르면 두 번 더해지므로 그 경우 가산금 0.
- **청소보증금은 할인 뒤에 더한다** — 지인할인(×0.8)이 보증금까지 깎으면 안 된다. 플랫폼 결제 건과
