# 구글캘린더 ↔ 예약현황 양방향 연동 — 확정 설계

**상태: 1단계(DB 준비) 완료 — `supabase/calendar-sync.sql`.** 다음은 2단계(구글 쪽 준비).

도메인(카페24에서 구매 예정)은 **5단계의 구글 푸시 알림에만** 필요하다.
1~4단계와 `지금 동기화` 단추·화면 열 때 동기화는 도메인 없이 전부 된다.
**푸시 단계에 도달하면 코드를 쓰기 전에 사장님께 "도메인 구매하셨나요?"를 먼저 묻는다** (사장님 요청).

2026-10-02 설계 합의, 2026-10-08 1단계 완료.

## 목적과 우선순위
1. **중복예약 방지** (1순위) — 폰 캘린더에 넣은 예약이 공개 달력에도 즉시 반영돼야 한다.
2. **거래기록 축적** (2순위)

둘 다 중요하지만 1순위 때문에 "아무도 admin을 안 보고 있을 때도 서버가 최신"이어야 한다.
공개 예약현황 달력은 손님이 언제든 보기 때문이다. (이것이 단방향으로 충분한 ShifShifAlarm과의 결정적 차이)

## 확정된 결정

| 항목 | 결정 |
|---|---|
| 연동 대상 | 구글캘린더에 **전용 캘린더를 새로 만들어** 연동 (개인 일정과 분리) |
| 인증 | **서비스 계정** + 그 캘린더만 "변경 권한"으로 공유 (OAuth 토큰 갱신 불필요) |
| 삭제 처리 | 구글에서 지워도 **ledger 행은 지우지 않고 "구글에서 삭제됨" 표시만** |
| 동기화 방향 | 양방향 |
| 17:00~18:00 공백 | 청소·정비 시간. 일정으로 넣지 않음 (낮·밤 다른 고객 사례 0건이라 잠정 보류) |

## 슬롯 ↔ 시각 매핑

| 패키지 | 구글 일정 시각 |
|---|---|
| 낮 | 10:00 ~ 17:00 (7h) |
| 밤 | 18:00 ~ 23:00 (5h) |
| 밤+밤샘 | 18:00 ~ **익일 09:00** |
| 전일 | 10:00 ~ **익일 09:00** (23h) |

밤+밤샘과 전일은 종료 시각이 같다 → **시작 시각(18시 vs 10시)으로 구분**한다.
제목에 패키지가 적혀 있으면 제목이 우선.

### 구글 → 예약현황 슬롯 판정

| 일정 시간 | 판정 |
|---|---|
| 종일(All-day) | 전일 |
| 시작 ≤ 12:00, 종료 17:00~18:00 | 낮 |
| 시작 17:00~20:00, 종료 같은 날 | 밤 |
| 시작 17:00~20:00, 종료 다음날 | 밤+밤샘 |
| 시작 ≤ 12:00, 종료 다음날 | 전일 |
| 그 외 | 기타 + `시간 확인 필요` 띠, 금액 추정 안 함 |

제목의 패키지와 실제 시간이 어긋나면 **제목을 따르고 `시간 불일치` 띠**를 단다.

## 요금표 (2026-10-02 사장님이 Supabase settings.prices 수정 완료)

| 패키지 | 월~목 | 금·공휴일 전날 | 토·일·공휴일 |
|---|---|---|---|
| 낮 | 40,000 | 40,000 | 110,000 |
| 밤 | 80,000 | 110,000 | 170,000 |
| 전일 | 100,000 | 180,000 | 260,000 |

금액 추정은 기존 `suggestAmount()`를 그대로 쓴다 (공휴일·공휴일 전날 판정 포함).
밤샘 +30,000 (전일은 무료), 청소보증금 +50,000 (지인·기타 채널 제외), 지인 총액 20% 할인.

## 제목 형식

```
패키지 / 이름 / 채널 / 콘텐츠
```

예: `전일 / 김민수 / 네이버 / 홀덤`, `밤+밤샘 / 박영희 / 지인 / 시계피 6명`, `낮 / 이철수`

**형식에 안 맞아도 최대한 읽는다.** 읽는 순서:
1. 패키지 — `전일`/`하루종일`/`밤샘`/`밤`/`낮` 키워드를 위치 무관하게 찾음. 없으면 시간으로 판정
2. 인원 — `6명`, `12인`
3. 연락처 — `010-xxxx-xxxx`
4. 채널 — `네이버`/`스페이스`/`아워`/`지인`/`별도`
5. 금액 — `150,000원`, `15만`
6. 콘텐츠 — `홀덤`/`시계피`/`머더`
7. 이름 — 남은 토막

설명란에 `키: 값`(이름/인원/채널/금액/연락처/메모)을 쓰면 제목보다 우선해서 읽는다.

## 금액 추정 규칙
- 날짜 + 슬롯으로 기본 요금을 추정한다. 채널·인원을 못 읽으면 보증금·지인할인·인원추가는 빠진다.
- 추정 건은 **`금액 추정` 띠 + 미정산**으로 넣는다. 사장님이 `확정`을 누르면 띠가 사라진다.
- `정산 완료만` 집계에는 애초에 들어가지 않으므로 확정 매출을 오염시키지 않는다.

## 무한 반복(메아리) 방지
1. 우리가 만든 일정에 숨은 꼬리표 `extendedProperties.private.ledger_id`를 넣는다.
   우리 일정은 이 꼬리표에서 정확한 값을 읽으므로 **왕복해도 정보가 깎이지 않고, 파싱이 필요 없다.**
   파싱은 사장님이 폰에서 직접 만든 일정에만 쓴다.
2. `calendar_links` 표에 거래 ↔ 구글 일정 짝 + 마지막으로 맞춘 내용의 지문(해시)을 저장.
   지문이 같으면 건드리지 않는다.
3. 양쪽이 동시에 바뀌면 **나중에 수정된 쪽이 이긴다.** 이긴 쪽·진 쪽을 `sync_log`에 남겨 되돌릴 수 있게 한다.

## 동기화 시점 — 도메인 구매 후 푸시로 간다
개인 도메인이 있으면 구글 **푸시 알림(watch)** 을 쓸 수 있다 → 변경 즉시(1초) 반영,
주기 폴링·깃허브 액션이 필요 없다. `*.vercel.app`은 도메인 소유 증명이 불가해서 못 썼다.

도메인 준비 후 체크리스트:
1. 카페24에서 도메인 구매
2. Vercel 프로젝트에 도메인 추가 (DNS: 카페24에서 A/CNAME 또는 네임서버 변경)
3. Google Search Console에서 도메인 소유 증명 (DNS TXT 레코드)
4. Google Cloud Console의 해당 프로젝트에 **도메인 등록** (푸시 콜백 주소 허용)
5. `events.watch` 로 채널 개설 → 만료 전 자동 갱신 로직 필요 (채널 수명 최대 ~30일)

푸시가 막히거나 지연될 때를 위해 **`지금 동기화` 단추**와 **화면 열 때 동기화**는 함께 넣는다 (안전망).
거래 저장·수정·삭제 시 구글 반영은 그 자리에서 즉시 호출한다 (이 방향은 도메인과 무관하게 항상 실시간).

## 단계별 계획
1. ~~**DB 준비**~~ ✅ **완료** — `supabase/calendar-sync.sql`
   `calendar_links`(짝 맞춤·지문), `sync_log`(되돌리기용 기록), `ledger.amount_estimated`(금액 추정 띠),
   `settings.slot_hours`(슬롯 시각). 임시 Postgres에 2회 실행해 재실행 안전성과
   cascade·기록 보존·중복 방지를 확인했다. *(사장님: Supabase에서 1회 실행)*
2. **구글 쪽 준비** — Calendar API 켜기, 서비스 계정 생성, 키를 Vercel 환경변수에, 전용 캘린더 공유. *(사장님: 약 15분, 클릭 단위 안내 예정)*
3. **구글 → 예약현황 미리보기만** — 실제로 쓰지 않고 "이렇게 들어올 예정" 표를 보여줌. 매핑 확인 후 `가져오기`.
4. **예약현황 → 구글** — 저장·수정·삭제 즉시 반영 + 기존 23건 일괄 내보내기(미리보기 후).
5. **구글 → 예약현황 자동** — `syncToken` 증분 동기화 + `지금 동기화` 단추·화면 열 때 (도메인 불필요).
   그 다음 **푸시 채널 개설 — 여기서 도메인이 필요하므로 사장님께 먼저 묻는다.**
6. **겹침 경고** — 같은 날 같은 슬롯 2건이면 경고 띠 (막지는 않음).

## 주의할 점
- 서비스 계정 키·도메인 DNS 정보는 **git에 넣지 않는다** (작업 규칙 6). Vercel 환경변수와 클라우드 환경 Secrets에만.
- 공개 달력은 `public_reservations` 창(날짜·패키지만)을 쓰므로 **손님에게 고객명·연락처가 보이지 않는다.** 이 구조를 유지한다.
- 구글에서 들어온 건은 금액을 모르므로 0원·미정산으로 들어간다 → `금액 추정` 띠로 눈에 띄게 한다.
